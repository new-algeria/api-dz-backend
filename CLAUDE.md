# data-dz-api

API publique de data-dz (https://api.data-dz.com). Hono + TypeScript sur Vercel (zéro config, entrée `src/index.ts`).
Le front est le dépôt `data-dz` (React) ; ce dépôt remplace l'ancienne API Express (api-dz-backend).
Référence complète des routes, de la mise en production et du script de synchronisation : `README.md`.

Commandes : `npm run dev` (Node 22, `.env` copié de `.env.example`), `npm test`, `npm run typecheck`.
Node 22 obligatoire, y compris en local : sous Node 20, supabase-js plante à la création du client (WebSocket natif absent).

## Règles
- **Aucun secret dans le dépôt.** `.env*` est ignoré sauf `.env.example`. La clé secrète Supabase ne sert que dans `supabaseAdmin()`, après `exigerAdmin`.
- **Données non redistribuables** (`datasets.diffusion_restreinte`) : jamais de fichier, de ligne ni d'aperçu (`ressources` vide, 403 `not_redistributable` dans `fichiersDe()`), seulement `lien_paquet`. Toute nouvelle route qui lit R2 doit passer par `fichiersDe()` ou vérifier `estRestreinte()`.
- **Jamais de clé de stockage R2 dans une réponse** : les fichiers sortent par `lienSigne()` (lien de 10 min) derrière `/download`. Le domaine public `files.data-dz.com` est réservé à `web-assets/`.
- Lectures publiques avec `supabasePublic()` (clé publishable) : la RLS décide de ce qui est visible.
- Toute réponse publique pose sa politique de cache (`mettreEnCache`) ; toute route admin est `no-store`.
- Erreurs : lever `ErreurApi` (message sûr à afficher, sans détail interne) ; `onError` répond en `application/problem+json`.
- Paramètres validés par zod dans `createRoute` ; une nouvelle route publique doit être documentée (OpenAPI) et testée dans `test/app.test.ts` si elle a une logique propre.
- Réponses < 4 Mo (limite Vercel 4,5 Mo) : au-delà, passer par un lien signé.
- Noms métier en français (`listerDonnees`, `lienTelechargement`), routes et champs d'URL en anglais, comme le front.
- Erreur de base : `erreurBase()` (admin) et `erreurSupabase()` (public) écrivent toujours le code Postgres dans les logs Vercel ; dans `erreurBase()`, 42703 (colonne inconnue = migration non appliquée) répond 503 `schema_outdated`. Une colonne ajoutée par une migration récente se lit avec `avecColonnesRecentes()` (liste `COLONNES_RECENTES`, ancien nom `avecIllustration()`) tant que la migration peut manquer.

- **Droits d'administration** : `exigerAdmin` accepte `CLE_SYNCHRO` ou un membre admin / dont le rôle porte la permission de la route (`permissionRequise()` : `synchro.gerer` pour `/v1/admin/sync`, sinon `donnees.gerer`). Liste des permissions dans `src/lib/permissions.ts`, identique à la contrainte `roles.permissions` de la base et à `src/lib/roles.ts` du site : les trois changent ensemble.
- **Fichiers par source** : `fichiers.source_id` / `licence_code` (migration 20261102000017), lus via le marqueur `SOURCE_FICHIERS` des `select` (retiré tant que la migration manque) ; chaque ressource sort avec `source` et `licence_code`.
- **Synchronisation population** : `scripts/population/` (calcul Python sur les grilles WorldPop, publication et rapport en TypeScript avec le client de `scripts/osm/api.ts`) et `.github/workflows/population-sync.yml` ; ligne `population` de `synchronisations`, mêmes routes `/v1/admin/sync/:code` que la synchro OSM. Voir le README.
- **Synchronisation OpenStreetMap** : `scripts/osm/` (README, section dédiée) et `.github/workflows/osm-sync.yml`. Jamais Overpass dans le robot (seul le bouton « tester » de l'admin fait un `out count`). Les fichiers OSM s'ajoutent aux précédents, rien n'est supprimé. Les flux (tag → donnée → fichier) sont en base (`osm_flux`, `src/lib/osm-flux.ts`) ; `categories.ts` est le secours. Format d'une expression : `src/lib/osm-format.ts`, partagé avec le robot.

- **Synchronisation sécheresse ERA5-Land** : `scripts/secheresse/` télécharge ERA5-Land mensuel par blocs, agrège les cellules dans les 69 wilayas (poids cos(latitude)), calcule normales/anomalies, SPI-3/SPI-12 et humidité du sol ; l'archive depuis 1981 est conservée et le JSON de 60 mois sert à la carte choroplèthe. Les précipitations de 09/2022–02/2024 sont reprises du produit `monthly_averaged_reanalysis_by_hour_of_day` à 00:00 (défaut ECMWF). Secret GitHub `CDS_API_KEY` (jeton CDS personnel), plus `API_URL` / `CLE_SYNCHRO` ; workflow `.github/workflows/secheresse-sync.yml`, ligne `secheresse` de `synchronisations` et migration data-dz `20261114000024`.
- **Synchronisation NASA FIRMS** : `scripts/wildfires/` collecte les produits NRT MODIS / VIIRS sur sept jours UTC, associe les points aux 69 wilayas GeoAlgeria, puis publie les fichiers NASA sous CC0-1.0 et les fichiers enrichis GeoAlgeria sous ODbL-1.0 ; clé `FIRMS_MAP_KEY` dans les secrets GitHub, workflow `.github/workflows/wildfires-sync.yml` et ligne `wildfires` de `synchronisations`.
- **Synchronisation des séismes USGS NEIC/PDE** : `scripts/seismes/` interroge le catalogue `us` / contributeur `us` depuis 1973 (M ≥ 2,5), associe les épicentres aux 69 wilayas GeoAlgeria et produit une série annuelle, une carte ponctuelle et des comptes annuels par wilaya ; fichiers source CC0-1.0 et enrichissements GeoAlgeria ODbL-1.0. Workflow `.github/workflows/seismes-sync.yml`, synchronisation `seismes` et migration data-dz `20261115000026`.

- **Synchronisation de l'équipe d'Algérie de football (hommes)** : `scripts/football/` (CSV CC0 de martj42/international_results), donnée `equipe-algerie-foot-m`, fichier principal `bilan-annuel` (courbe) et `infos_source.nb_enregistrements` (nombre de matchs, chiffre de la carte du catalogue). Buteurs partiels : jamais de classement. Workflow `.github/workflows/football-sync.yml`, synchronisation `equipe-algerie-foot-m`, migration data-dz `20261120000031`.

- **Statistiques datées** : `compterEvenementDonnee(slug, evenement, contexte)` (`src/lib/catalogue.ts`) appelle `enregistrer_evenement_donnee` (compteur + ligne de `evenements_donnees`, migration data-dz `20261120000032`), repli sur `compter_evenement_donnee` si la fonction manque. `/download` = origine `api`, `/download-link` (bouton du site, lien en JSON, compte via `membreFacultatif()`) = origine `site`, `/view` = vue sans compte. Une statistique ne fait jamais échouer un téléchargement.

- **Vignettes du catalogue** (`/v1/datasets/{slug}/thumbnail.webp`) : dessin pur dans `src/lib/vignette.ts` (testé, aucun texte, fond transparent), lecture et cache R2 dans `src/lib/vignette-image.ts` (chargé à la demande, sharp). Changer le dessin ? Incrémenter `VERSION` pour recalculer toutes les vignettes.
- **Chiffres par wilaya** (`src/lib/wilayas.ts`, routes `/v1/wilayas` et `/v1/wilayas/{code}`) : pour chaque donnée publiée qui recense des lieux, nombre d'enregistrements par wilaya (code du fichier, sinon point dans les contours `wilaya-boundaries` de `divisions-administratives`), population de `population-wilayas`. Fichier principal par défaut, exceptions dans `FICHIERS_PAR_DONNEE` (à compléter si le principal d'une nouvelle donnée n'est pas son inventaire). Décomptes rangés dans R2 (`exports/wilayas/v1/…`, clé = empreinte du fichier et des contours) ; budget de 45 s, réponse `complet: false` (cache 30 s) si dépassé. Les données non redistribuables ne sont jamais comptées.

## Tests (à étendre)
Vitest couvre la conversion, la validation des paramètres, la limite de débit et quelques erreurs. À prévoir : routes publiques et admin avec un Supabase et un R2 simulés (liste, fiche, `/data`, `/download`, création, version, illustration), et un contrôle du schéma de la base cible (chaque colonne lue par l'API existe) avant chaque déploiement.


- **Synchronisation des températures (NASA POWER)** : `scripts/temperatures/` interroge l'API « daily point » de NASA POWER (sans clé) au chef-lieu des 69 wilayas (bureau de poste principal de la commune chef-lieu, fichiers `wilayas` et `postoffices` de `divisions-administratives`), depuis 1981 ; synthèses mensuelles, annuelles et nationales (jours ≥ 35 / 40 °C, nuits ≥ 20 °C, écart à la normale 1991–2020). Estimations de réanalyse (maille ≈ 50 km), jamais présentées comme des relevés. Fichier quotidien en CSV seulement (1,16 million de lignes). Workflow `.github/workflows/temperatures-sync.yml`, synchronisation `temperatures`, migration data-dz `20261125000033`. Open-Meteo écarté (limite gratuite par IP).

- **Synchronisation électricité Ember** : `scripts/electricite/` extrait les séries annuelles du CSV mondial Ember pour DZA, garde les lignes par filière et les agrégats marqués, construit une synthèse par année et publie en JSON/CSV. Licence CC BY 4.0, attribution Ember ; workflow `.github/workflows/electricite-sync.yml`, ligne `electricite` de `synchronisations` et migration data-dz `20261115000027`. La période disponible est détectée, sans extrapolation. Voir le README du script.

- **Synchronisation pétrole et gaz (EIA)** : `scripts/petrole-gaz/` lit le fichier groupé `INTL.zip` de l'EIA (sans clé, domaine public, licence `PDM-1.0`), garde 8 séries annuelles de l'Algérie (brut, liquides, LGN, consommation de pétrole, exportations de brut ; production, consommation et exportations de gaz) et publie `petrole-gaz-algerie` (principal `series-annuelles` en format long, `bilan-annuel` en large). Valeurs absentes jamais mises à zéro, plages plausibles contrôlées ; découpage brut / condensats / LGN variable selon les années chez l'EIA, expliqué dans la fiche. Workflow `.github/workflows/petrole-gaz-sync.yml`, synchronisation `petrole-gaz` (30 jours), migration data-dz `20261126000034`.

- **Synchronisation pêche et aquaculture (FAO FishStat)** : `scripts/peche-aquaculture/` lit la dernière édition de `GlobalProduction_<édition>.zip` (CC BY 4.0, sans clé), garde l'Algérie (code ONU 012, tonnes de poids vif) et publie `peche-aquaculture-algerie` : `production-annuelle` (principal, format long, 7 filières, `part_officielle_pct`), `production-par-espece`, `especes-principales`. La FAO estime les années non déclarées (statut « I ») : toujours dire « estimation FAO » pour ces années (2024 dans l'édition 2026.1.0). Workflow `.github/workflows/peche-aquaculture-sync.yml`, synchronisation `peche-aquaculture` (30 jours), migration data-dz `20261126000035`.

- **Synchronisation Banque mondiale (WDI)** : `scripts/banque-mondiale/` interroge l'API v2 (sans clé, CC BY 4.0) pour 36 indicateurs de l'Algérie depuis 1960 (`INDICATEURS` : unité, thème, plage plausible, estimation modélisée) et publie `indicateurs-developpement-algerie` : `indicateurs-annuels` (principal, format long `annee` / `indicateur` / `valeur` / `unite` seulement), `bilan-annuel` (une colonne par code), `dictionnaire`. Source data-dz `banque-mondiale` (existante). Workflow `.github/workflows/banque-mondiale-sync.yml`, synchronisation `banque-mondiale` (30 jours), migration data-dz `20261127000036`.
- **Fichier principal en format long** : la fiche du site fait une série par combinaison de colonnes texte (hors `code`, `id`…, `MOTIF_EXCLU` de `detecterVisuel.ts`). Ne garder que `indicateur` comme colonne texte, ou nommer les autres `code_…` (d'où `code_serie_eia` dans `petrole-gaz`).

- **Synchronisation production agricole (FAOSTAT)** : `scripts/agriculture/` lit le fichier groupé `Production_Crops_Livestock_E_Africa.zip` (CC BY 4.0, sans clé), garde l'Algérie (`Area Code` 4) et publie `production-agricole-algerie` : `principales-productions` (principal, 30 séries en format long avec `code_statut`), `production-detaillee`, `classement-produits`. `derniere_annee_officielle` (2021 dans le fichier du 31/12/2025) : les années suivantes sont des estimations ou imputations de la FAO, toujours le dire. Source data-dz `fao` (existante). Workflow `.github/workflows/agriculture-sync.yml`, synchronisation `agriculture-fao` (30 jours), migration data-dz `20261128000037`.
